## 一、概述

本方案基于对项目全部核心代码的深度审计，涵盖主进程 12 个文件和前端 15 个文件，共发现 **7 个 P0、18 个 P1、21 个 P2、6 个 P3** 级别问题。升级目标：

1. **消除数据丢失风险** — 修复配置文件写入竞态和云同步 TOCTOU 问题
2. **堵住安全漏洞** — 修复路径遍历、SSRF、凭据泄露等安全问题
3. **消除内存泄漏** — 修复事件监听器、定时器、Promise 挂起等资源泄漏
4. **统一架构** — 消除状态管理碎片化，建立清晰的进程边界
5. **提升性能** — 消除不必要的重渲染、串行请求、阻塞操作

## 三、P0 问题详解与修复方案

### P0-01: 配置文件写入竞态 — read-modify-write 数据丢失

**文件**: `src/main/services/configService.js:43-56`

**问题**: `writeSettings` 使用 `fs.writeFileSync` 直接覆盖目标文件。`readSettings` 和 `writeSettings` 都是同步操作且无互斥锁，多个 IPC handler（保存设置、云同步、自动同步）可并发执行 `readSettings → 修改 → writeSettings`，产生经典的 read-modify-write 竞态：两个 handler 同时读到同一版本，各自修改后依次写入，后者覆盖前者的修改。

**修复方案**:

```javascript
// configService.js — 引入写队列 + 原子写入

let _writeQueue = Promise.resolve()

/**
 * 原子写入：先写临时文件，再 rename 替换
 */
function writeSettingsAtomic(data) {
  const tmpPath = SETTINGS_PATH + '.tmp'
  fs.writeFileSync(tmpPath, JSON.stringify(data, null, 2), 'utf-8')
  fs.renameSync(tmpPath, SETTINGS_PATH) // 同文件系统上 rename 是原子的
}

/**
 * 串行化写入：所有写操作通过队列依次执行
 */
function writeSettings(data) {
  _writeQueue = _writeQueue.then(() => {
    // 备份
    if (fs.existsSync(SETTINGS_PATH)) {
      fs.copyFileSync(SETTINGS_PATH, SETTINGS_PATH + '.bak')
    }
    writeSettingsAtomic(data)
  }).catch(err => {
    logger.error('写入配置失败:', err)
    throw err
  })
  return _writeQueue
}

/**
 * 串行化读取-修改-写入：在同一个队列任务中完成
 */
async function readModifyWrite(modifier) {
  return new Promise((resolve, reject) => {
    _writeQueue = _writeQueue.then(() => {
      const data = readSettings()
      const modified = modifier(data)
      if (fs.existsSync(SETTINGS_PATH)) {
        fs.copyFileSync(SETTINGS_PATH, SETTINGS_PATH + '.bak')
      }
      writeSettingsAtomic(modified)
      resolve(modified)
    }).catch(reject)
  })
}
```

### P0-02: 云同步 push/pull 双重 readSettings 导致 TOCTOU 覆盖

**文件**: `src/main/services/SyncService.js:283-302` (push), `321-380` (pull)

**问题**: `push` 方法在 `_runExclusive` 闭包内先 `readSettings()` 提取数据，然后写入元数据时再次 `readSettings()`。两次读取之间，其他 IPC handler 可能已修改并写入了磁盘文件。第二次 `readSettings` 读到的是新版本，但 push 将其与旧元数据合并写入，丢失中间的修改。`pull` 方法同样存在此问题。

**修复方案**: 在 `_runExclusive` 闭包内只读取一次 settings，后续所有修改都基于该对象，最后一次性写入。使用 `configService.readModifyWrite()` 替代多次 `readSettings() + writeSettings()`。

### P0-03: WebDAV 凭据明文存储且 authorize() 返回原始凭据

**文件**: `src/main/services/cloud/WebDAVProvider.js:18-25, 136`

**问题**: `username` 和 `password` 作为实例属性明文存储，`_authHeader` 是 Base64 编码的凭据。`authorize()` 方法将 `accessToken`（Base64 编码的凭据）返回给调用方，扩大了凭据暴露面。

**修复方案**:
1. `authorize()` 改为返回布尔值 `{ success: true }` 或 token 标识，不返回原始凭据
2. 添加 `dispose()` 方法，在不再使用时清零 `password` 和 `_authHeader`
3. 扩展 `CryptoManager.js` 的 `SENSITIVE_KEYS` 以包含 `password`、`token`、`secret`、`credential`、`accessToken`、`refreshToken`

### P0-04: 路径遍历漏洞 — delete-skill / import-skill-online

**文件**: `src/main/ipc/skills.js:113, 152-153`

**问题**: `delete-skill` 和 `import-skill-online` 直接将 `name` 参数拼接到 `SKILLS_FOLDER`，执行 `fs.rmSync` 或写入操作。如果 `name` 为 `../../.iflow` 或 `../../.ssh`，会删除或覆盖用户主目录下的任意目录/文件。

**修复方案**:

```javascript
// 安全路径校验工具函数
function validateSafePath(baseDir, name) {
  // 名称格式校验
  if (!/^[a-zA-Z0-9_.:-]+$/.test(name)) {
    throw new Error(`Invalid name: ${name}`)
  }
  // 路径遍历校验
  const resolved = path.resolve(baseDir, name)
  if (!resolved.startsWith(path.resolve(baseDir) + path.sep) && resolved !== path.resolve(baseDir)) {
    throw new Error(`Path traversal detected: ${name}`)
  }
  return resolved
}
```

在 `delete-skill`、`import-skill-online`、`read-command`、`update-command`、`delete-command` 中统一使用。

### P0-05: App.vue 系统主题监听器未移除

**文件**: `src/App.vue:880`

**问题**: `onMounted` 中通过 `window.matchMedia(...).addEventListener('change', updateSystemTheme)` 注册了系统主题变化监听器，但 `onUnmounted` 中为空，未调用 `removeEventListener`。HMR 场景下会累积监听器。

**修复方案**:

```javascript
const mediaQuery = window.matchMedia('(prefers-color-scheme: dark)')
const updateSystemTheme = () => { ... }

onMounted(() => {
  mediaQuery.addEventListener('change', updateSystemTheme)
})

onUnmounted(() => {
  mediaQuery.removeEventListener('change', updateSystemTheme)
})
```

### P0-06: IPC 事件监听器累积

**文件**: `src/App.vue:779-830`

**问题**: `initUpdateListeners` 注册了多个 IPC 事件监听器（`onUpdateStatusChanged`、`onUpdateAvailable` 等），均未在组件卸载时移除。若组件被重新挂载（HMR），会累积重复监听器，导致事件回调多次执行。

**修复方案**: 保存每个监听器的清理函数，在 `onUnmounted` 中逐一调用：

```javascript
const unsubscribers = []

function initUpdateListeners() {
  unsubscribers.push(
    window.electronAPI.onUpdateStatusChanged(callback),
    window.electronAPI.onUpdateAvailable(callback),
    // ...其他监听器
  )
}

onUnmounted(() => {
  unsubscribers.forEach(fn => fn?.())
  unsubscribers.length = 0
})
```

同时在 `preload.js` 中确保所有 `onXxx` 方法返回 unsubscribe 函数。

### P0-07: 渲染进程导入主进程代码

**文件**: `src/components/QuickAddDialog.vue:83`

**问题**: `import { parseMcpInput, ensureUniqueName } from '../main/utils/mcpParser'` 直接从渲染进程导入主进程代码。如果 `mcpParser.js` 引入任何 Node.js API，渲染进程会崩溃。这是架构上的反模式，违反 Electron 安全模型。

**修复方案**: 将 `mcpParser.js` 移动到 `src/shared/` 目录，确保其不依赖任何 Node.js API。验证其代码中仅使用纯 JavaScript 逻辑（正则、字符串处理等），无 `fs`、`path`、`require` 等 Node.js 调用。

## 四、P1 问题详解与修复方案

### P1-01: _runExclusive 代码结构脆弱

**文件**: `src/main/services/SyncService.js:82-96`

**问题**: `_runExclusive` 先设置 `this.isSyncing = true`，然后才创建 promise 并赋值给 `this._currentSyncPromise`。代码结构脆弱，未来重构时容易引入竞态。

**修复**: 将 `this._currentSyncPromise` 赋值移到 `isSyncing` 之前，或用 `try/finally` 包裹整个方法体。

---

### P1-02: _getOrCreateDeviceId 非原子写入

**文件**: `src/main/services/SyncService.js:940-947`

**问题**: 先 `readSettings()` 检查 deviceId 是否存在，若不存在则生成新 UUID 并再次 `readSettings() + writeSettings()` 写入。两次读取之间其他进程可能已写入不同的 deviceId。

**修复**: 使用 `configService.readModifyWrite()` 保证原子性。

---

### P1-03: WebDAVProvider 无重定向次数限制

**文件**: `src/main/services/cloud/WebDAVProvider.js` (`_request` 方法)

**问题**: `_request` 不处理 HTTP 3xx 重定向，`_ensureDir` 的重试逻辑可能因重定向响应而误判。

**修复**: 在 `_request` 中显式处理 3xx 响应，设置最大重定向次数（5 次），检查重定向 URL 的 scheme 不低于原始请求。

---

### P1-04: save-settings 合并策略未保护内部管理字段

**文件**: `src/main/ipc/settings.js:18-23`

**问题**: `const merged = { ...existing, ...data }` 允许渲染进程覆盖 `_deletedProfiles`、`_deletedServers`、`pushPending` 等内部管理字段。

**修复**: 对这些字段做与 `cloudSync` 同样的保护：

```javascript
const PROTECTED_FIELDS = ['cloudSync', 'autoUpdate', '_deletedProfiles', '_deletedServers', 
                          'pushPending', 'deviceId', 'lastSyncTime', 'lastSyncError']

const merged = { ...existing, ...data }
PROTECTED_FIELDS.forEach(field => {
  if (existing[field] !== undefined) {
    merged[field] = existing[field]
  }
})
```

### P1-05: import-skill-online URL 无校验 — SSRF 风险

**文件**: `src/main/ipc/skills.js:108-109`

**问题**: 直接使用渲染进程传入的 `url` 发起 HTTP 请求，可构成 SSRF 攻击（访问 `127.0.0.1`、`169.254.169.254` 等）。

**修复**:
1. 校验 URL scheme 必须为 `https:`
2. 禁止请求私有 IP 地址段
3. 使用 `validator.js` 中已有的 `validateUrl` 函数

### P1-06: import-skill-online 仅处理一级重定向

**文件**: `src/main/ipc/skills.js:118-123`

**问题**: 仅处理一次 3xx 重定向，且重定向时使用与原始请求相同的 protocol 模块。HTTPS→HTTP 降级会泄露数据。

**修复**: 实现最大重定向次数限制的循环，检查重定向 URL 的 scheme 不低于原始请求。

## 六、架构级改进

### 6.1 统一状态管理

**现状**: App.vue 和各视图组件大量使用本地 `ref` + `window.electronAPI` 直接操作，绕过了 Pinia store 层，导致状态逻辑分散。

**目标**: 所有业务状态通过 Pinia store 管理，组件仅通过 store 读写数据。

**步骤**:
1. 将 App.vue 中的 `settings`、`apiProfiles`、`currentApiProfile` 逻辑迁移到对应的 Pinia store
2. 组件通过 `useSettingsStore()`、`useApiProfilesStore()` 访问数据
3. 移除组件中的 `window.electronAPI` 直接调用，改由 store 封装
4. 确保 store 的 `load()` 和 `save()` 方法正确处理异步和错误

### 6.2 IPC 事件监听器生命周期管理

**现状**: Electron IPC 事件监听器（`onXxx`）普遍缺少对应的清理机制。

**目标**: 建立统一的注册/清理机制。

**步骤**:
1. 在 `preload.js` 中，所有 `onXxx` 方法返回 unsubscribe 函数
2. 在 `src/composables/` 中创建 `useIpcListener` composable，自动在组件卸载时清理
3. 全局监听器（如 store 中的）在应用退出时清理

```typescript
// src/composables/useIpcListener.ts
export function useIpcListener() {
  const unsubscribers = ref<(() => void)[]>([])
  
  function on(event: string, callback: (...args: any[]) => void) {
    const unsub = window.electronAPI[`on${event}`]?.(callback)
    if (unsub) unsubscribers.value.push(unsub)
  }
  
  onUnmounted(() => {
    unsubscribers.value.forEach(fn => fn())
  })
  
  return { on }
}
```

### 6.3 配置文件写入安全模型

**现状**: `configService.js` 的读写操作无互斥保护，多个并发写入可导致数据丢失。

**目标**: 所有对 `settings.json` 的写操作串行化，且使用原子写入。

**步骤**:
1. 引入写队列（`serializeWrites`），确保所有写操作串行执行
2. 使用临时文件 + `rename` 的原子写入模式
3. 提供 `readModifyWrite()` 方法，消除 read-modify-write 竞态
4. 所有 IPC handler 和 SyncService 统一使用新接口

### 6.4 渲染进程/主进程边界清晰化

**现状**: `QuickAddDialog.vue` 直接导入主进程代码 `mcpParser.js`。

**目标**: 主进程代码和渲染进程代码严格分离，共享代码放在 `src/shared/`。

**步骤**:
1. 将 `mcpParser.js` 移动到 `src/shared/`
2. 验证其不依赖任何 Node.js API
3. 建立 ESLint 规则，禁止渲染进程代码导入 `src/main/` 下的模块

### 6.5 参数校验统一化

**现状**: 各 IPC handler 各自实现参数校验，标准不一，部分 handler 完全无校验。

**目标**: 建立统一的参数校验中间件。

**步骤**:
1. 在 `src/main/utils/validator.js` 中扩展校验工具：
   - `validateSafePath(baseDir, name)` — 路径遍历防护
   - `validateUrl(url, options)` — SSRF 防护
   - `validateConfigName(name)` — 配置名称格式
   - `validateUuid(id)` — UUID 格式
2. 在 `src/main/ipc/index.js` 中注册 IPC handler 时支持校验中间件
3. 对所有接受渲染进程输入的 IPC handler 应用校验

## 九、风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 原子写入 rename 在不同文件系统间失败 | Windows 下跨盘符 rename 失败 | 使用 `fs.copyFileSync` + `fs.unlinkSync` 作为 fallback |
| 写队列引入导致保存延迟 | 用户感知保存变慢 | 队列内操作通常 <10ms，用户无感知 |
| URL 校验误拦合法地址 | 用户无法配置内网 API | 允许 `localhost`/`127.0.0.1`，仅禁止云元数据端点 |
| 状态管理统一引入大量重构 | 可能引入新 bug | 分阶段迁移，每阶段独立测试 |
| preload.js 返回 unsubscribe 函数需改接口 | 现有代码兼容性 | 保持现有 `onXxx` 调用方式不变，新增返回值 |
